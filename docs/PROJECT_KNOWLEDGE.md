# DevDocs Agent：项目知识复盘

这不是按 Day 1～16 重抄课程表，而是按代码实际运行的路径梳理：**每一层解决什么问题、出了错怎么定位、怎样验证自己真的会了。** 文件链接指向当前实现；课程计划里的设想不等于已经实现的功能。

## 1. 项目到底是什么？

**最准确的定位：本地文档 RAG 问答原型，外加一个受控的工具调用循环。**

- **RAG（检索增强生成）**：先从知识库找证据，再把证据交给模型回答。更新知识通常是更新文档与索引，不是重新训练模型。
- **固定工作流**：应用代码决定先检索、再回答。模型不负责选择下一步。[Day11](../langgraph_day11.py) 虽然用了 LangGraph，但图实际是固定的 `START → retrieve → answer → END`；无证据时在节点内部提前返回，不是图上的条件边。
- **Agent**：[Day12](../agent_day12.py) 让模型决定是否调用 `search_docs`、`read_source`，但由 Python 决定哪些请求能执行。LangGraph 只包装了一个 Agent 节点，真正的循环在 `run_agent()` 里。**装了 LangGraph 不等于做了 Agent，没用 LangGraph 也能实现工具循环。**
- **Agent harness**：这里指模型之外负责工具接入、状态、预算、权限、故障处理等的运行层。本项目有应用专用的最小 harness 机制，但还不是可以拿来运行不同 Agent 的通用运行框架。没有必要用「生产级 Agent Harness」包装它。另一个容易混淆的词是 **test harness**：Day8 的固定样本、评分和报告属于检索评测脚手架，不是 Agent 运行框架。

## 2. 先读通两条问答路径

| 入口 | 代码实际怎么走 | 用它理解什么 |
| --- | --- | --- |
| [Streamlit](../streamlit_app.py) | Chroma Top 3 → 证据检查 → `llm.answer()` 生成并校验引用；Chroma 异常时尝试关键词检索 | 固定 RAG 流程，检索证据可以在页面查看 |
| [FastAPI](../api_day15.py) 的 `POST /chat` | `safe_turn()` → `ask_turn()` → `run_agent()` → 模型可调用 `search_docs`（混合检索＋重排）和 `read_source` | 用户输入如何经过上下文补全、模型决策、工具执行和错误包装 |

这两条路径**没有共享全部保障**。例如，[Day6 `llm.answer()`](../llm.py) 会程序化检查引用；Agent 路径主要靠提示词约束输出，在回退总结时也没有复用同一套引用校验。知道一项能力写在哪个文件还不够，要确认当前入口真的走到了那里。

## 3. 文档如何变成可检索的证据（Day 1～5、7）

| 知识点 | 在本项目中怎么做 | 应该理解的取舍 |
| --- | --- | --- |
| 文档加载与元数据 | [retriever.py](../retriever.py) 读知识库第一层的 UTF-8 Markdown/TXT，保存来源、行号、Chunk ID 等信息；[upload_utils.py](../upload_utils.py) 校验上传文件名、大小和编码 | 正文用于匹配，元数据用于定位和引用。上传成功不等于文件内容已进入向量索引 |
| Chunk 切分 | 按空行分段，过长再按字符拆分，默认上限 240 字符。当前没有滑窗重叠 | 太短会丢失上下文，例如单独一个标题；太长会混入不相关主题。切片是检索质量的一部分，不是纯预处理细节 |
| 关键词与 Embedding | `keyword_retrieve()` 用连续双字重合；`semantic_retrieve()` 用本地 BGE 模型把问题和片段编码成向量，计算余弦相似度 | 字面匹配擅长编号和术语，向量能匹配部分同义表达。相似度是排序信号，不是答案正确的概率 |
| Chroma 与增量同步 | [vector_store.py](../vector_store.py) 将向量持久化；索引记录用来源、Chunk ID、正文的哈希作键。同步时比较 ID 集合，删除旧块、编码新增块，不重复编码未变块 | 对外的 Chunk ID 是证据定位标识，不等同于内部索引键；段落的位置变化也可能改变 Chunk ID。查询时编码的是问题，不是把全部文档重算一次 |

**复盘练习**：添加一条不含隐私的规则，先查索引，再调用 `sync_index()` 后查询，然后删除该规则并同步。记录 `added/removed/unchanged` 和返回的 `source/chunk_id`。重点不是问 AI「索引怎么更新」，而是自己预测每一步发生什么，再用输出验证。

## 4. 候选召回、重排与评测（Day 8～10）

1. **召回**：从知识库找一批可能相关的片段。向量检索看语义；[BM25](../hybrid_search.py) 还考虑词项频次、稀有程度和文档长度。这里 BM25 的中文词项是双字，不是完整的中文分词系统。
2. **融合**：两路分数尺度不同，不能直接把余弦分和 BM25 分相加。这里使用 RRF，按名次计算 `1 / (k + rank)` 并累加；两路都排得靠前的片段通常更占优。
3. **重排**：[Day10](../rerank_day10.py) 对混合检索候选用 query 词项覆盖率重新排序；这不是神经网络 Cross-Encoder。正确片段没有进入候选池时，重排无法把它变出来；已经召回的片段也可能被重排挤出前三名。重排失败或超时时回退到原候选顺序。
4. **Gold 与 Hit@3**：[Day8](../eval_day8.py) 用 [20 条人工标注](../evals/day8_cases.json) 配成固定对照。每条由「问题、预期来源、证据原文」组成。前三个片段中有一个同时匹配来源与原文，这道题才算命中。**Hit@3 测的是证据能否被检索出来，不是最终回答准确率。** 同名文件里的错误片段不算分，能回答问题但未被标注的替代证据也可能不算分。

**这次最值得复盘的结果**：对知识文档使用说明性标题并同步索引后，Day8 的纯 Chroma 路径由 18/20 到 20/20；同一套 Gold 上，Agent 使用的混合检索＋词项重排仍是 18/20。不是「技术栈越多效果越好」，也不能把 20 道已用于调优的题当作独立验证集。由于没有冻结独立样本，这次结果只能说明对这套题的回归表现；两个检索指标都不验证答案质量。

**复盘练习**：选 Q09 或 Q12，用相同问题分别取 `search_index()`、`hybrid_search()`、`safe_search()` 的结果。记录 Gold 在每一层的候选排名和最终排名，先回答「没召回，还是被挤出前三？」再决定该改召回还是重排。然后手写几条未参与调优的新问题，用同样口径另作一组测试，不改原 Gold。

## 5. 从证据到答案：提示词不是执行权限（Day 6、11～13）

- **证据门禁与引用**：[evidence.py](../evidence.py) 和 [llm.py](../llm.py) 会在固定 RAG 路径先检查证据，不够就不请求模型；生成后检查引用 ID 是否来自该次检索。**引用存在不等于引用支持了结论**，后者还要检查原文语义。检索到的文档是数据，不应该当作系统指令；提示词提示这点，但不能替代代码权限控制。
- **工具协议**：[Day12](../agent_day12.py) 把工具 schema 交给模型；模型返回的是 `tool_calls` 请求，不是工具已执行的证明。`dispatch()` 检查工具白名单、JSON 字段、类型和长度；`read_source` 只能读最近一次检索命中的 Chunk，不能传任意文件路径。一批请求中的每个执行结果要用相应的 `tool_call_id` 回填。
- **调用预算**：一次用户提问可包含最多两轮工具决策，之后可能另发一次总结请求。「每轮」是指**一次模型响应**。Day12 默认每次响应最多一个工具调用；[Day13](../day13_chat.py) 把这个上限设为三个。两个上限限制工作量和延迟，与工具权限是不同问题。
- **真实故障：超限与 DSML 输出**。最初检索已成功，下一次模型响应同时请求多个工具，旧程序却中止。后来允许受限批量调用，超限时跳过该批次，尝试用已取到的证据总结；总结也曾把工具标记当成正文返回。现在 Day13 的回退总结从一条新的无工具请求开始，只发送问题和证据；若仍出现已识别的 DSML 标记、工具调用或空输出，则展示证据摘录。**这是针对已观察到的协议异常做的兜底，不是通用模型输出净化器。**
- **多轮上下文**：Day13 按字符预算保留最近的完整问答；检测到「那」「它」「这个」等指代时，仅拼接上一轮用户问题，而不是每次发送全部历史。这样能复现「那它同步失败怎么办？」为什么需要上一问来解释「它」，但不是语义记忆，也不是精确的 Token 预算。

**复盘练习**：读 [Day12 的 Mock 回归](../tests/test_day12.py)，不调用付费 API，自己构造两种响应：「三次 `read_source`」和「超限后模型返回协议标记」。逐条解释哪些调用执行、哪些不执行、最终展示什么。再对照 [Day13 回归](../tests/test_day13.py)，解释为什么上下文补全正确也可能答不好。

## 6. 错误、HTTP 与真实测量（Day 14～16）

- **可观测性**：[Day14](../day14_trace.py) 将超时、限流等情况分类，用 JSONL 记录 `trace_id`、状态、错误类型和耗时；不依赖用户复述完整提示词才能定位故障。线程等待超时只说明调用方停止等结果，底层线程仍可能继续；不要把它讲成硬取消。当前也没有完整的逐次 Token 或成本记录。
- **HTTP 合约**：[Day15](../api_day15.py) 用 Pydantic 校验请求，调用方每次传需要的历史，没有服务端持久会话。`GET /health` 只证明服务在运行；浏览器打开未注册的 `/` 返回 404，不代表进程没起来。`POST /chat` 的正常和故障路径可在 `/docs` 试，服务绑定端口失败则先检查操作系统网络层，而不是改问答代码。
- **三种测试证明不同的事**：[HTTP Mock 测试](../tests/test_day15.py) 证明字段透传与状态码映射，不证明模型可用；Day8 使用真实本地索引测检索；[README](../README.md#实测指标) 中的约 1.76 秒是 3 次非流式短请求的平均单次模型 API 延迟，不含 RAG 检索，也不是首 Token 或多次调用的整轮耗时。
- **验收与发布**：[Day16](../final_audit_day16.py) 检查文件和样本、运行子进程并记录退出码与输出。检查项全通过不代表 Hit@3 满分，检索结果还要看评测脚本的输出。`.env`、本地报告、日志和索引不应随源码发布。当前依赖清单没有覆盖全部后期模块；若希望别人可复现，下一步应补齐依赖并在全新环境验证启动与测试。

## 7. 怎样把它变成能讲清楚的项目？

**可以作为初级岗位的辅助项目，但不必把它当旗舰项目。** 照课程接几个库本身区分度不高；如果能亲手复现一个问题、定位到具体层、写出回归并说明指标边界，就有可讲的工程证据。不要把 AI 生成的实现直接写成自己的设计经历，只写自己能独立复现和解释的贡献。

先挑一条主线，而不是再加三种框架：

- **想突出 RAG**：用保留的新题比较纯向量、混合、重排三条路径。分别记录命中率、失败样本和相同预热口径下的耗时。能解释哪层变好、哪层退化，比写「Hit@3 达 100%」更有说服力。
- **想突出 Agent 工程**：用 Mock 模型亲手重写一个小型工具循环，覆盖未知工具、参数非法、批量调用、预算耗尽以及总结兜底。再把工具注册与执行预算从文档业务中分离，用第二个简单任务验证能否复用。届时再评估是否值得定位为 harness。

简历表述参考（**独立复现后按实际贡献取舍**）：

> 实现本地研发文档 RAG 问答原型，支持 Chroma 增量索引、混合检索与受限工具调用；用固定人工标注集对比检索路径，并为批量工具调用及异常输出回退补充 Mock 回归测试。

最快的自测方式：不看文档，用三分钟讲清「问题如何找到证据 → 谁决定调用工具 → 模型出错时程序怎么处理」，再挑一次故障亲手复现。能把预期、观测和结论讲通，比记住每天新增了什么文件更有价值。
